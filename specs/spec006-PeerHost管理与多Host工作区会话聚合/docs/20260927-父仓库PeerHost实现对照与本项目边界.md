# 父仓库 PeerHost 实现对照与本项目边界

## 1. 文档目的

本文记录父仓库 CodingNS 中 PeerHost 相关实现的职责、可复用逻辑和不能直接复用的边界，为 `spec006-PeerHost管理与多Host工作区会话聚合` 的实现提供依据。

父仓库只作为行为、安全边界和数据流参考。本项目不能复制父仓库源码，也不能把父仓库运行时作为 npm、源码或进程依赖。

## 2. 父仓库实现位置与职责

### 2.1 `peer-hosts-api.ts`

路径：`/Users/jackson/Code/CodingNS/apps/user-app/src/features/workbench/api/peer-hosts-api.ts`

该模块是用户端 PeerHost 管理 API 封装，主要职责包括：

- 列出当前用户可管理的 PeerHost 记录。
- 创建、更新和删除 PeerHost 配置。
- 调用握手、登录、重连和删除目标会话接口。
- 将返回值转换为 Client 可显示的 DTO。

可以借鉴的逻辑：

1. 管理操作按 `peerHostId` 定位记录，不让 Client 自己拼接目标 Host URL。
2. 登录、检查、重连和删除使用明确的动作接口，错误可以单独显示。
3. Client 只处理脱敏状态、版本和连接结果，不读取目标 token。

本项目的边界：

- API 路径必须适配本项目已有 RPC/HTTP 入口，不能复制父仓库路由注册。
- DTO 必须使用本项目 `HostScope`、能力矩阵和错误码，不能直接导入父仓库类型。
- 当前工作区未必拥有父仓库的用户应用状态树，不能假设 `peer-hosts-api.ts` 的 store 可以直接移植。

### 2.2 `peer-host-service.ts`

路径：`/Users/jackson/Code/CodingNS/apps/host/src/modules/peer-host/peer-host-service.ts`

该服务是父仓库的 Host 侧核心，负责：

- 保存 PeerHost 记录和目标路由。
- 规范化地址并拒绝重复目标。
- 访问目标 Host 的握手接口。
- 保存目标 access/refresh token 和过期时间。
- 在代理请求前检查握手状态、登录态和 fingerprint。
- 目标登录失效、地址变化或身份变化时清理目标会话。

可以借鉴的逻辑：

1. PeerHost 凭据归当前 Host 管理，浏览器只提交目标记录 ID。
2. 握手结果是代理前置条件，失败目标不能伪装成空工作区。
3. fingerprint 变化必须使旧登录态失效。
4. 目标 token 刷新放在 Host 侧，当前 Host 登录态与目标登录态隔离。

本项目的边界：

- 存储必须接入本项目已有 Host settings/敏感存储边界，不能复制父仓库数据库或密钥实现。
- 目标 Host 的版本判断必须走 `src/dsh-capabilities/` 能力矩阵，不在服务中散落版本分支。
- 本项目的 `PeerHostRecord` 需要同时表达局域网和中转路由，但中转能力必须先经过单独探测。

### 2.3 `host-api-proxy-service.ts`

路径：`/Users/jackson/Code/CodingNS/apps/host/src/modules/peer-host/host-api-proxy-service.ts`

该服务提供当前 Host 到目标 Host 的 HTTP 受控代理，核心做法是：

- 从当前用户和 PeerHost ID 解析目标记录。
- 由 Host 侧生成目标 URL，不接受客户端任意 URL。
- 代理前调用 `ensureProxyReady` 和目标 token 获取逻辑。
- 过滤 Hop-by-Hop 头，注入目标 Bearer token。
- 使用允许的方法和路径集合拒绝认证、管理和递归代理接口。
- 将目标 401 转换为当前 PeerHost 的登录失效并清理目标会话。

可以借鉴的逻辑：

1. 代理目标必须来自已保存的 PeerHost 记录。
2. 白名单应按方法和路径正向登记，不能使用“所有 `/api`”规则。
3. 代理错误需要稳定错误码和 PeerHost 标识，便于 Client 说明真实状态。
4. 出站请求可以统一处理认证头和 Hop-by-Hop 头。

本项目的边界：

- 白名单必须覆盖本项目实际支持的文件、Git、终端和右侧工具接口，不能照抄父仓库的接口集合。
- 所有请求还必须增加 `HostScope` 校验和 `scopeGeneration` 约束。
- 目标响应不能把父仓库特有的内部字段直接暴露给本项目 Client。

### 2.4 `host-ws-proxy-service.ts`

路径：`/Users/jackson/Code/CodingNS/apps/host/src/modules/peer-host/host-ws-proxy-service.ts`

该服务提供工作台 WebSocket 代理，核心做法是：

- 只处理固定的 PeerHost WebSocket 路径。
- 当前 Host 先认证，再打开目标 Host 的工作台 WS。
- 客户端消息和远端消息分别使用白名单。
- 拒绝二进制消息和未知消息类型。
- 任一侧关闭时关闭另一侧；目标认证失败时清理目标会话。
- 对终端、会话和工作台消息记录脱敏诊断字段。

可以借鉴的逻辑：

1. 客户端 WS 不能直接连接任意目标地址。
2. 消息类型必须分别维护客户端和远端白名单。
3. 连接关闭、错误和上游认证失败必须有明确的生命周期处理。
4. 代理层不能把未知消息广播给其他连接。

本项目的边界：

- 必须把 `hostId/workspaceId/sessionId/scopeGeneration` 绑定到订阅和消息校验中。
- DSH 版本不同导致的消息差异要在能力 adapter 中处理，不能在代理里堆版本 `if`。
- 中转连接不一定支持父仓库的 `ws://target/ws?access_token=...` 方式，必须先验证 Host-to-Host Transport。

### 2.5 `WorkbenchHostSwitcher.tsx`

路径：`/Users/jackson/Code/CodingNS/apps/user-app/src/features/workbench/components/WorkbenchHostSwitcher.tsx`

该组件把当前 Host、直接 Host 和 PeerHost 的管理操作放在同一个用户界面中，包含：

- Host/PeerHost 列表和状态展示。
- 添加和编辑地址、别名、登录信息。
- 握手检查、重连、删除和目标资源状态查看。
- Host 标签颜色和别名处理。

可以借鉴的交互逻辑：

1. 状态、版本和最近检查时间应在管理入口集中展示。
2. 添加、登录、重连、删除是不同动作，应有独立进行中状态和错误提示。
3. Host 别名和标签颜色属于展示配置，不应改变 Host ID 或资源 key。

本项目的边界：

- 用户需求是“右下角连接管理按钮”，不等于把现有 active Host 切换器原样搬入。
- PeerHost 选择应改变资源作用域，而不是改变当前 Host 登录和全局配置。
- UI 需要遵守本项目的 Feature 启停、设置表单和 locale 规则。

## 3. 本项目可复用的核心思路

以下逻辑可以作为 spec006 的稳定原则：

1. **当前 Host 代理目标 Host**：Client 只提交 `targetHostId`，凭据和目标地址留在当前 Host。
2. **握手后才允许业务请求**：产品标识、插件版本、DSH 版本、API 兼容标识和 fingerprint 缺一不可。
3. **HTTP/WS 受控代理**：固定入口、固定目标、固定路径和固定消息类型。
4. **登录态分层**：当前 Host 登录态、每个 PeerHost 登录态互相隔离。
5. **状态可解释**：插件缺失、版本不兼容、身份变化、未登录、不可达和中转不可用必须区分。
6. **连接生命周期绑定**：目标 WS、订阅、缓存和 Host 记录删除/停用时一起失效。

## 4. 不能直接复用的部分

### 4.1 父仓库的应用状态和路由

父仓库使用自己的用户应用状态、Host 配置和路由注册方式。本项目已有 `FeatureRegistry`、能力矩阵、Host/Client 入口和远程 Web 运行时，直接复制会造成两套配置来源和生命周期。

实现时必须把父仓库逻辑翻译为本项目内部契约，而不是保留父仓库 import 路径或运行时对象。

### 4.2 父仓库的 Host 切换语义

父仓库的 `WorkbenchHostSwitcher` 同时管理 active Host 和 PeerHost。spec006 的核心需求是聚合多 Host 资源，因此不能把“选择 PeerHost”实现为替换 active Host。选择 PeerHost 只改变 `HostScope.targetHostId`，当前 Host 的登录、设置和代理入口不变。

### 4.3 父仓库的 API 白名单

父仓库白名单反映父仓库当时支持的工作台接口。本项目 DSH 版本、已实现 Feature 和远程 Web 运行时不同，必须为每个新增路径补能力矩阵、契约测试和安全测试。

### 4.4 父仓库的中转连接假设

浏览器可以使用现有中转入口，并不代表当前 Host Node 进程可以使用同一 Transport 去连接另一台 Host。中转 PeerHost 必须单独验证：

- Host-to-Host 身份认证和授权。
- 双向 HTTP/WS 转发能力。
- ticket 生命周期和刷新。
- 断线恢复和目标 fingerprint 校验。
- 不把任意公网 URL 暴露成代理目标。

验证完成前，中转 PeerHost 只能显示 `relay_unavailable` 或等价降级状态。

## 5. DSH 0.1.6 与当前项目的特殊限制

当前调查表明，DSH 0.1.6 的原生导航能力主要围绕单一 `remote.workspace` / `remote.session` 作用域设计，未必提供把多个 Host 的工作区树和会话树合并到同一个原生导航组件的稳定扩展点。

因此分两个层次实现：

1. **原生聚合路径**：能力矩阵确认存在稳定导航 adapter 后，使用内部 HostScope 和聚合 DTO 接入三栏 UI。
2. **Remote Web Context 降级路径**：没有稳定 adapter 时，使用 `src/client/remote-web-context.ts` 挂载目标 Host 的远程 Web 内容，并明确显示降级状态。

Remote Web Context 可以验证远端登录、页面和部分交互链路，但不能宣称它已经实现了完整的原生多 Host 三栏聚合。中栏消息、聊天框和右侧栏若仍由远端页面内部渲染，必须在验收中标记为降级能力。

## 6. 禁止事项

- 禁止复制父仓库源码并保留其内部 import 路径。
- 禁止把父仓库作为运行时 npm 依赖或通过进程调用获得 PeerHost 能力。
- 禁止让 Client 保存目标 Host access/refresh token。
- 禁止接受客户端任意 `baseUrl`、完整 URL 或任意 WebSocket 地址。
- 禁止用裸 `workspaceId` 或 `sessionId` 作为跨 Host 全局 key。
- 禁止在中转能力未验证时静默回退到任意公网 URL。
- 禁止把 Remote Web Context 降级描述成完整原生三栏聚合。

## 7. 实现前的证据要求

开始阶段 2 之前，应至少准备：

1. 当前项目 Host/Client 能力矩阵中的 PeerHost route 草案。
2. 局域网目标 Host 的握手 fixture 和 fingerprint fixture。
3. 目标登录态的敏感存储测试。
4. DSH 0.1.6 的 Remote Web Context 行为记录。
5. 中转 Host-to-Host 能力探测结论；若未通过，任务清单必须保持 relay 阶段为 `BLOCKED` 或 `degraded`，不能把它标记为 ready。
